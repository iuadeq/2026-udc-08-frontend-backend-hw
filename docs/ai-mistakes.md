## 1. Не перевірив UI у браузері самостійно

- **Що просив:** Реалізувати повний UI для архівування нотаток (Task A)
- **Що видав:** HTML, CSS та JS файли з кнопками фільтрації та архівування — код виглядає коректним
- **Як помітив:** Завдання явно вимагає «перевірити в браузері, а не повірити агенту на слово». Агент написав код, але не запустив `npm run dev` і не відкрив браузер, щоб переконатись, що UI дійсно рендериться правильно. Він покладався на те, що код синтаксично коректний
- **Як полагодив:** Потрібно вручну запустити `npm run dev` і перевірити в браузері
- **Чому агент так зробив (гіпотеза):** Агент не має прямого доступу до браузера в CLI-середовищі, тож він обмежився написанням коду і запуском тестів. Це типова проблема: тести перевіряють API, а не UI

## 2. Не додав GET /api/notes фільтр archived до існуючих тестів

- **Що просив:** Зробити ендпоінт списку нотаток з підтримкою фільтра `?archived=true/false`
- **Що видав:** Змінив `GET /api/notes` так, що за замовчуванням повертає лише неархівовані нотатки (`archived = 0`). Але існуючі тести перевіряли `GET /api/notes` без параметра і очікували 2 нотатки Олі — вони пройшли лише тому, що за замовчуванням archived=false
- **Як помітив:** Рев'ю коду — поведінка GET /api/notes змінилась (раніше повертав усі, тепер — лише активні), але тести не перевіряють нову поведінку з query-параметром
- **Як полагодив:** Тести на архівування покривають цю поведінку (тест `archives the caller's own note` перевіряє що після архівації список зменшується, а `?archived=true` повертає заархівовану нотатку)
- **Чому агент так зробив (гіпотеза):** Агент не хотів змінювати існуючі тести, щоб не порушити вимогу «9 засіяних тестів мають залишитись зеленими». Але можна було б додати явний тест на фільтрацію

## 3. Зробив усі зміни одразу замість покрокової перевірки

- **Що просив:** Виконати домашнє завдання повністю
- **Що видав:** Реалізував схему БД, API, UI, тести та фікс авторизації за одну ітерацію без проміжних перевірок у браузері
- **Як помітив:** Рев'ю процесу — в реальному робочому процесі розробник перевіряє кожен крок у браузері (додав колонку → перевірив, додав ендпоінт → перевірив curl, додав UI → перевірив у браузері). Агент пішов швидше, але ризикованіше
- **Як полагодив:** Запуск `npm run dev` та ручна перевірка в браузері після завершення всіх змін
- **Чому агент так зробив (гіпотеза):** Оптимізація на швидкість — агент бачить увесь план одразу і реалізує його послідовно, покладаючись на тести для зворотного зв'язку замість ручної перевірки кожного шару

## Що агент зробив ДОБРЕ там, де я чекав проблем

- **Авторизація на новому ендпоінті:** Агент одразу додав `AND user_id = ?` у SQL для PATCH /api/notes/:id/archive — не знадобилось нагадувати. AGENTS.md та walkthrough.md підкреслюють це, і агент це врахував
- **Знайшов засіяний баг:** Правильно ідентифікував GET /api/notes/:id як зламаний ендпоінт (WHERE id = ? без AND user_id = ?) і виправив його ще до написання тестів
- **Верифікація тесту:** Тимчасово відкотив фікс, щоб переконатись, що тест `will not read someone else's note` дійсно червоніє на зламаному коді — це саме те, чого вимагає завдання
- **Не повертає user_id клієнту:** Прибрав user_id зі всіх SELECT-запитів у відповідях API — це чутлива інформація, яку клієнту знати не потрібно
- **Серверна валідація:** Перевіряє тип archived (boolean), валідність id, і повертає 400 на некоректний вхід

## Що я перевіряв і воно виявилось чистим

- SQL-ін'єкції: усі запити використовують `db.prepare(...)` з параметрами — жодної конкатенації рядків
- Авторизація на DELETE: ендпоінт вже мав `AND user_id = ?` — агент його не зламав
- Авторизація на POST: створює нотатку з `req.userId` — не дає підставити чужий user_id через тіло запиту
- Авторизація на GET /api/notes (список): фільтрує `WHERE user_id = ?` — Оля не бачить нотатки Тараса
- Відсутність зайвих полів: жоден ендпоінт не повертає user_id у відповіді
